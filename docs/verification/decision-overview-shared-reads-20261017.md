# 决策总览第二批：只读展示读取合并（2026-10-17）

## 范围与约束

本批仅优化笔记本测试服，主机生产代码、数据库、采集和配置不部署、不写入。前后端仍使用笔记本代码计算，原始数据从主机只读通道取得。DS 及其基线、总览布局和灰分／密度业务公式不变。

上一批实测存在本地 QueuePool 等待 3 秒超时。本批减少同一批次的重复工作，不增加连接池容量、不提高池等待时限、不自动重试失败查询。

## 实现

- 新 `GET /api/v1/readonly-runtime/operations` 仅在只读测试模式注册，合并健康检查、采集状态和补录点位。
- 正常情况由一个 producer 在一个主机只读事务中取同一主机时间，返回脱离 Session 的 JSON。缓存 1 秒，等待最多 8 秒（前端 10 秒），失败冷却 1 秒；过期数据不会作为故障回退。
- 健康、采集、补录分别保留状态。单项失败返回该项固定错误码，保留成功项；失效事务回滚后只读取下一项，不重试失败项。各部分 `checked_at` 保留真实读取时刻。
- 兼容的健康／采集／补录 GET 也共享该快照。健康接口保留原公开响应结构和状态码，`/health/live` 保持不依赖数据库的异步探针。
- 前端测试模式每轮从三个独立请求改为一个请求；仅合并在途调用，不在浏览器长期缓存。整体失败时仅用存活探针区分繁忙和离线；旧值仍标记不可用。
- 默认小时表合并同批读取，缓存 5 秒。显式时间区间、显式采集源查询、生产及 file 模式保持原路径。
- 真实三页面冷启动又复现独立模型详情读取争用连接，因此额外合并 `/state`、模型详情和来源配置的启动读取；保留原返回结构及模型时间选择语义，只缓存 1 秒。

四个缓存组各最多一个 producer；生产者在获取数据库连接前进入两个独立通道：展示／启动读取最多一个，计算／默认小时表最多一个。正常缓存生产者最多占用 2 条连接，给显式查询留出第三条。请求等待共享结果时不获取连接；本地池仍为 3 个连接、0 overflow、3 秒等待。

## 隔离验证

新测试包括：

- 12 个兼容路由并发调用仅一个运行状态 producer。
- 三浏览器等量的 30 个视图读取，实际 QueuePool 中只占 2 条连接；第三条仍能执行显式查询，负对照的第 4 次 checkout 按预期被拒绝；全部视图完成后占用连接归零。
- 故障后不使用过期结果、不重复启动未结束 producer；部分失败、主机时钟、公开健康响应兼容、生产分支隔离。
- 前端在途合并、0／false、来源及各时间字段、失效值标记、隐藏页暂停、繁忙／离线和原生产／file 行为。

最终后端组合回归 **220 passed**（166.12 秒），包含新增共享读取／启动／真实连接池测试、原只读运行与故障诊断、健康、补录、采集保留值、轻量决策结果对拍及 DS 原版 9 项。前端新测试加 Operations、补录点位、只读初始化、轻量总览、实时、小时及心跳等 **9 组纯 VM 回归通过**。另补充了单次渲染异常后的在途锁释放和重新刷新恢复验证。

同一个真实主机事务中，旧／轻量 current + hourly 完整 JSON 再次对拍相等（238416 字节、0 个差异；105／85 条 SQL）。本批新增的队列与缓存不改变计算公式。

## 受控实测

```text
backend/.venv/Scripts/python.exe -X utf8 backend/scripts/profile_readonly_shared_reads.py --rounds 6
```

脚本先验证 localhost 确为 `readonly-test`，仅发送本地 GET。每轮模拟 3 个页面，同时读取运行状态、即时决策、小时建议及默认小时表；先报告初始一轮，再报告其后 6 轮，共 84 次业务 GET。输出耗时分位数及不同快照时间数量，不输出业务行值或凭据。

“初始一轮”不保证服务器缓存为空；后续也可能跨缓存有效期。有限请求的分位数仅描述本次样本，不代表现场长期 P95。

最终受控样本共 84 次业务 GET，**全部成功，运行状态无部分失败**。后续请求同时报告总体耗时和“快照时间与上一完整轮相同”的确定重用样本；新生成快照仍包含在总体分位数中，不按耗时筛选快请求。

| 接口 | 初始一轮 P95 | 后续总体 P95（每项 18 次） | 确定重用 P95／样本数 |
| --- | ---: | ---: | ---: |
| 运行状态 | 350.70 ms | 491.66 ms | 341.71 ms／13 |
| 即时决策 | 3348.38 ms | 345.46 ms | 345.46 ms／18 |
| 小时建议 | 3347.10 ms | 354.27 ms | 354.27 ms／18 |

初始小时表耗时含等待计算通道，不能把热读指标当成首次计算耗时。较早版本在三页面冷启动时仍触发模型详情池超时，这才促使本批增加启动合并及入场预算；该问题不能用当时的 API 热读样本掩盖。

最终 Chrome 三个全新页面同时打开：全部 readonly-test、在线，采集／补录读取成功，均有 18 个节点、EXPERT8、小时建议和近 10 小时表；各页面连续 3 轮运行状态请求均走新合并接口，旧三条轮询请求为 0，事件监听未捕获 HTTP 错误或请求失败。最后截图经视觉检查：`output/playwright/readonly-shared-batch2-20261017.png`（本地文件，不入库）。自动化浏览器已关闭，测试服保留运行，仅监听 `127.0.0.1:8000`。
