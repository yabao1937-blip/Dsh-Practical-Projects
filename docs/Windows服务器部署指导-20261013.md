# 重介密控系统 Windows 服务器部署指导

目标服务器地址为 10.255.1.21，仅供厂内访问。2026 年 10 月 13 日用户截图确认该机为 Windows Server 2008 R2 Standard SP1、64 位、VMware 虚拟机，内存 16 GB。该系统不在 Python 3.11 的官方支持范围内，下面的 Python 3.11 安装和服务模板不能直接用于这台旧服务器。[Python 官方 Windows 支持说明](https://docs.python.org/3.11/using/windows.html)

建议保留旧服务器上的 KEPServer，由另一台支持 Python 3.11 的厂内主机或新虚拟机运行 Web、collector 和本机 SQLite，通过 opc.tcp://10.255.1.21:49320 采集。新主机地址待确定；网页应访问新主机 IP。下文安装目录与 Windows 服务模板供兼容的新 Windows 主机使用，其中 Web 绑定地址需替换为新主机 IP，OPC 地址仍为旧服务器地址。

当前锁定 NumPy、SciPy 和 scikit-learn 依赖要求 Python 至少 3.11，源码也使用较新 Python 能力；不能只安装 Python 3.8 继续照搬。当前新主机方案仍采用单个 Uvicorn Web worker、本机 SQLite 和独立采集服务，使用 Windows 服务实现开机启动、失败重启和日志轮转。以下路径是建议目录，确认新主机磁盘空间后可统一替换。

本次交付是部署指导及参考资料，未在服务器上安装软件、复制业务数据库或启动采集。部署不重训模型，不修改 DS 分支和 backend/data/train_js.json。

> 🧠 **From Hindsight memory (重介密控：决策总览与小时简报共享数据来源)** — 决策总览和小时简报共享 KEPServer、手工补录与 GPT 保存模型。已核对当前代码；当前每 5 秒决策归档由 Web 生命周期任务运行，不能沿用旧记录另开独立决策进程的描述。

## 建议部署方式

| 组件 | 运行位置和职责 |
|---|---|
| Web 服务 | 10.255.1.21:8000，FastAPI 同时托管前端和 API，1 个 worker |
| 采集服务 | 同一服务器，collector.py 只读采集 OPC UA，向同一 SQLite 写入 |
| SQLite | C:\DMCSData\dense_medium.db，放本机持久磁盘 |
| 采集缓存 | C:\DMCSData\telemetry-spool，保留断线或入库故障后的待写批次 |
| 日志 | C:\DMCSData\logs，Web 和采集分别轮转 |
| 服务托管 | 两个 Windows 服务，开机自动启动，进程失败后重启 |

现有采集配置为 opc.tcp://10.255.1.21:49320，50 个点位，每 5 秒读取并保存历史。旧服务器该端口正在监听且已有客户端连接。新主机上的 collector 需验证到该端口的网络和 OPC UA 会话；TCP 监听本身不替代真实采集验证。

前端无需 npm 构建；从新主机的 HTTP 地址访问页面。下文 http://10.255.1.21:8000/ 是系统版本确认前的草案地址，在新主机方案中应统一替换，不能把新主机 Web 进程绑定到旧服务器 IP。

FastAPI 的常驻服务需要进程托管。项目的 run.py 开启 reload=True，适合开发；现有后台启动和 watchdog 脚本也不等于开机系统服务。[FastAPI 部署概念](https://fastapi.tiangolo.com/deployment/concepts/)

## 第一步 核对服务器

在已连接的服务器 PowerShell 中执行以下只读检查：

~~~powershell
Get-CimInstance Win32_OperatingSystem | Select-Object Caption,Version,OSArchitecture
Get-CimInstance Win32_Processor | Select-Object Name,NumberOfCores,NumberOfLogicalProcessors
Get-CimInstance Win32_ComputerSystem | Select-Object @{Name='MemoryGiB';Expression={[math]::Round($_.TotalPhysicalMemory/1GB,1)}}
Get-Volume | Select-Object DriveLetter,FileSystem,SizeRemaining,Size
Get-NetIPAddress -AddressFamily IPv4 | Select-Object IPAddress,PrefixLength,InterfaceAlias
Test-NetConnection 10.255.1.21 -Port 49320
Get-NetTCPConnection -LocalPort 8000 -State Listen -ErrorAction SilentlyContinue
py -0p
~~~

49320 的 TCP 检查成功只证明端口可达；实际 OPC UA 会话和点位仍需后续单批验证。8000 已占用时先识别进程，不直接停止现有应用。安装 Python 前确认 Windows 版本和架构与安装包兼容。[Python Windows 安装说明](https://docs.python.org/3.11/using/windows.html)

硬件暂可按 4 核、8 GB 内存及至少 100 GB 可用 SSD 空间作初始规划；这是未经过服务器负载测试的建议。同机已有 KEPServer 时，要以它的正常运行资源余量为前提。上线后测量实际内存、CPU 和数据库增长再调整。

## 第三步 迁移现有数据库

本项目应迁移现有生产数据。GPT 激活模型保存在 SQLite 的 gpt_coarse_model_revisions 表中，DS 保存模型、来源选择、补录、小时简报、反馈和决策证据也依赖完整数据库。只复制模型 JSON，或只导出前端 CSV/state，无法还原完整系统。

先在维护窗口停止旧电脑上本项目的 Web 和 collector，保全未落库 spool 批次。然后用 SQLite Online Backup API 创建完整一致快照；不要直接复制正在使用的 .db。WAL 可能仍包含已提交事务。[SQLite 在线备份](https://www.sqlite.org/backup.html)、[SQLite WAL 文件](https://www.sqlite.org/wal.html)

以下示例在当前开发电脑执行，不是在服务器执行。目标备份文件必须不存在：

~~~powershell
New-Item -ItemType Directory -Path 'D:\DMCS-transfer' -Force
@'
from pathlib import Path
import sqlite3
import sys

source = Path(sys.argv[1]).resolve()
target = Path(sys.argv[2]).resolve()
if target.exists():
    raise SystemExit("目标备份已存在，请使用新文件名")
with sqlite3.connect(source.as_uri() + "?mode=ro", uri=True) as src:
    with sqlite3.connect(str(target)) as dst:
        src.backup(dst)
        result = dst.execute("PRAGMA integrity_check").fetchone()[0]
        if result != "ok":
            raise SystemExit("备份完整性检查失败：" + result)
print("完整快照已创建")
'@ | & 'D:\dense-medium-density-control-system\backend\.venv\Scripts\python.exe' - 'D:\dense-medium-density-control-system\backend\data\dense_medium.db' 'D:\DMCS-transfer\dense_medium.db'
Get-FileHash -LiteralPath 'D:\DMCS-transfer\dense_medium.db' -Algorithm SHA256
~~~

将快照复制到服务器 C:\DMCSData\dense_medium.db，核对文件哈希。不要覆盖服务器已有数据库。kepserver.local.json、模型辅助文件及待写 spool 如需迁移，应与快照一起保全；旧运行 PID 和锁不迁移。

先在快照的另一份副本上核对结构、模型激活状态和启动兼容升级，再正式切换。当前 app.main 导入时会 create_all 和兼容升级，启动 Web 不是只读检查。正式切换后旧电脑不再运行独立生产采集，避免两边数据分叉；复制到两份不同库时，采集租约不能阻止这种情况。

## 第四步 核对迁移版本

服务器当前终端设置数据库地址后，在 backend 目录执行：

~~~powershell
$env:DMCS_DATABASE_URL = 'sqlite:///C:/DMCSData/dense_medium.db'
.\.venv\Scripts\python.exe -m alembic heads
.\.venv\Scripts\python.exe -m alembic current
~~~

2026 年 10 月 13 日源码中的 head 为 c3a610120001。旧版接入文档写的 c3a610060001 已过时，实际以随本次代码交付的 heads 输出为准。

对于已有数据库，先核对 alembic_version 与实际表结构。没有版本但已经存在业务表时，不直接执行 upgrade head 或 stamp head。只有确认迁移基线适配，并在副本验证通过后，才升级正式库。

只有确实采用空数据库重新安装时，才在首次启动 Web 前执行以下命令；它不能替代现有数据和模型的迁移：

~~~powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
~~~

迁移应一次执行，避免由多个工作进程同时负责。[Alembic 迁移教程](https://alembic.sqlalchemy.org/en/latest/tutorial.html)

## 第五步 前台联调

在服务器的两个 PowerShell 窗口中分别运行。第一窗口启动 Web：

~~~powershell
Set-Location 'C:\DMCS\backend'
$env:DMCS_DATABASE_URL = 'sqlite:///C:/DMCSData/dense_medium.db'
$env:DMCS_ALLOW_LOCALHOST_WRITES = '0'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 10.255.1.21 --port 8000 --workers 1 --no-proxy-headers
~~~

第二窗口校验采集配置、读取单批，成功后再持续运行：

~~~powershell
Set-Location 'C:\DMCS\backend'
$env:DMCS_DATABASE_URL = 'sqlite:///C:/DMCSData/dense_medium.db'
$env:DMCS_TELEMETRY_SPOOL = 'C:\DMCSData\telemetry-spool'
.\.venv\Scripts\python.exe collector.py --config config\kepserver.local.json --validate
if ($LASTEXITCODE -ne 0) { throw '采集配置校验失败，停止部署' }
.\.venv\Scripts\python.exe collector.py --config config\kepserver.local.json --once
if ($LASTEXITCODE -ne 0) { throw '单批读取失败，停止部署' }
.\.venv\Scripts\python.exe -u collector.py --config config\kepserver.local.json
~~~

--validate 不连设备、不写数据库；--once 会实际连接 KEPServer 并写入一批数据。仅在旧生产采集已停止、迁移库检查完成后运行。单批结束的来源状态可能显示停止；持续采集启动后再验收 connected 和新时间戳。

现有配置采用匿名 None 安全策略，不加密 OPC UA 通信；保持 49320 在受控现场网络中。要切换加密需同时配置服务端信任和客户端证书，不能只改一个配置字段。

生产保持 1 个 worker：小时简报和 5 秒决策归档随 Web 生命周期启动。虽然代码有数据库事务和主键去重，多 worker 仍会多开后台循环、争抢 SQLite 写锁。Uvicorn CLI 的 --host 和 --workers 明确固定部署行为，不使用开发热重载。[Uvicorn 配置文档](https://github.com/Kludex/uvicorn/blob/main/docs/settings.md)

## 第六步 开机常驻与日志

联调通过后，先停止前台 Web 和采集，再将两者配置成 Windows 服务。推荐使用 WinSW 官方稳定 2.x 发行包，并阅读该版本对应文档；官方当前把 3.x 标为预发行系列。[WinSW 官方项目](https://github.com/winsw/winsw)、[2.x 使用说明](https://github.com/winsw/winsw/blob/v2/README.md)

下载与服务器兼容的发行包，把可执行文件各复制一份，命名 DMCS-Web.exe 和 DMCS-Collector.exe，放在 C:\DMCS\Services。对应 XML 与 exe 同名并放在同一目录。Web 示例：

~~~xml
<service>
  <id>DMCS-Web</id>
  <name>DMCS Web</name>
  <description>Dense medium web and hourly background tasks</description>
  <executable>C:\DMCS\backend\.venv\Scripts\python.exe</executable>
  <arguments>-u -m uvicorn app.main:app --host 10.255.1.21 --port 8000 --workers 1 --no-proxy-headers</arguments>
  <workingdirectory>C:\DMCS\backend</workingdirectory>
  <env name="DMCS_DATABASE_URL" value="sqlite:///C:/DMCSData/dense_medium.db"/>
  <env name="DMCS_ALLOW_LOCALHOST_WRITES" value="0"/>
  <env name="DMCS_TELEMETRY_SPOOL" value="C:\DMCSData\telemetry-spool"/>
  <startmode>Automatic</startmode>
  <stoptimeout>60 sec</stoptimeout>
  <onfailure action="restart" delay="10 sec"/>
  <logpath>C:\DMCSData\logs</logpath>
  <log mode="roll-by-size">
    <sizeThreshold>10240</sizeThreshold>
    <keepFiles>8</keepFiles>
  </log>
</service>
~~~

采集 XML 使用同样的目录、日志和重启配置，修改 id/name，并用以下字段替换 Web 的 executable、arguments 和 env；不保留 Web 专属参数：

~~~xml
<executable>C:\DMCS\backend\.venv\Scripts\python.exe</executable>
<arguments>-u collector.py --config C:\DMCS\backend\config\kepserver.local.json</arguments>
<env name="DMCS_DATABASE_URL" value="sqlite:///C:/DMCSData/dense_medium.db"/>
<env name="DMCS_TELEMETRY_SPOOL" value="C:\DMCSData\telemetry-spool"/>
~~~

使用经配置的服务账号，赋予代码读取、配置读取、SQLite 所在目录和 spool/logs 写入权限；不使用交互桌面账号的临时目录。当前代码仍会创建 backend/data 和 backend/models，需让相关目录可用。写 token 不设置时在 backend/data/write_token.txt 生成，应保护该文件；DMCS_DATABASE_URL 不会改变 token 路径。不能将 token 设为 off。普通 .env 文件不会被本项目自动加载，配置应注入两个服务的环境。

确认配置和服务账号后，在管理员 PowerShell 安装并启动指定服务：

~~~powershell
Set-Location 'C:\DMCS\Services'
.\DMCS-Web.exe install
.\DMCS-Collector.exe install
.\DMCS-Web.exe start
.\DMCS-Collector.exe start
Get-Service DMCS-Web,DMCS-Collector
~~~

XML 语法与日志参数依据 [WinSW 2.x XML 配置](https://github.com/winsw/winsw/blob/v2/doc/xmlConfigFile.md) 和 [日志轮转](https://github.com/winsw/winsw/blob/v2/doc/loggingAndErrorReporting.md)。这些示例尚需目标机运行验收。安装后用服务管理器停止指定服务，避免按端口强制终止其他应用。

不宜同时启用旧保持在线脚本、任务计划启动器和新 Windows 服务。服务托管应只有一个责任主体；采用本方案时也不要再通过网页的采集启停入口另起进程。

## 第七步 厂内网络访问

8000 入站只允许已确认的厂内客户端 IP 或网段，限制在服务器的 10.255.1.21 网卡上。先从网络管理员处取得允许网段，再创建规则；不要根据 10.255.1.21 猜测实际掩码。

将下方占位文本替换为真实厂内网段或客户端 IP，再在管理员 PowerShell 执行：

~~~powershell
$FactoryClients = @('替换为确认的客户端IP或CIDR')
New-NetFirewallRule -DisplayName 'DMCS Web Factory' -Direction Inbound -Action Allow -Protocol TCP -LocalAddress 10.255.1.21 -LocalPort 8000 -RemoteAddress $FactoryClients -Profile Domain,Private
~~~

检查服务器当前网络 Profile。若实际为 Public，应与管理员确认相应规则；不要关闭整机防火墙。用另一台厂内电脑访问 http://10.255.1.21:8000/ 验收，仅服务器自身访问成功不足以证明厂内可用。

首页会向访问者提供写 token，这不是账号登录系统。允许访问端口的范围也应是允许操作该系统的人员范围。

如厂内要求 HTTPS 或另有访问网关，可随后在同机增加反向代理，Web 改绑 127.0.0.1，并配置可信转发来源。整个页面和 API 都转发给 backend，以保留首页 token 注入。force=true 的本机限制依赖真实客户端 IP；代理不能把所有客户端变成回环地址。首次直接厂内访问方案无需引入代理。[Uvicorn 代理来源说明](https://www.uvicorn.org/deployment/)

## 第八步 验收与后续运行

依次核对：

1. http://10.255.1.21:8000/ 能打开；/api/v1/health/live 和 /api/v1/health/ready 均正常。
2. /api/v1/telemetry/latest 显示实际 connected，预期点位数量和质量正确，时间戳持续前进。
3. /api/v1/gpt-coarse/current 返回现行激活模型；决策来源、手工补录、DS/GPT 保存模型、旧简报和反馈均保留。
4. 对照切换前样本，确认输入、预测与建议密度；缺数、停机和断线时仍遵守原保护规则。
5. 关闭所有浏览器后，等一个整点再确认小时简报和归档继续生成。
6. 断开远程桌面后服务继续工作；维护窗口重启服务器后，两个服务自动恢复。
7. 隔离环境执行下面的 DS 原版对拍，必须实际通过，不能将缺基线导致的 skip 当成通过；不运行基线生成器。
8. 完成一次从完整备份恢复到另一个目录的演练，确认数据库、激活模型与历史均可读取。

~~~powershell
Set-Location 'C:\DMCS\backend'
.\.venv\Scripts\python.exe -m pytest -q tests\test_training.py
~~~

ready 仅检查部分必要表，不代表采集在线或模型正确。服务器首次上线的验收要覆盖真实 KEPServer 会话、模型和后台任务。

每日安排完整数据库一致快照并保存到独立备份位置；按 2026-10-14 的永久存储要求，原始历史、决策档案和恢复备份均不设置自动淘汰期限。配置定时备份时也不要启用按天数或份数删除旧备份。force 覆盖前备份不是每日定时备份服务。重启策略看进程退出或 live；ready 或采集异常应分别告警，避免因数据库暂时故障反复重启。

文档初次检查时主库约 642 MiB，仅是当时某一时刻的文件大小。50 点、5 秒间隔的理论上限约 864000 个点位历史行每天，实际以部署点表为准。2026-10-14 起原始采集历史永久保留；逐次决策的 7 天热表转换只是无损压缩归档，归档数据仍长期保存。记录上线后一周的实际日增量、备份空间和剩余容量，并据此扩容。

切换失败时停止新服务，先保全新服务器新增数据和日志，再恢复旧端；不把旧快照直接覆盖新库。代码回滚是否兼容新结构应先验证，不能用 Alembic downgrade 当作默认回滚操作。

## 当前代码依据

- backend/run.py 与 backend/serve.py：开发和常驻启动入口。
- backend/app/main.py：自动兼容升级、Web 生命周期和同源静态托管。
- backend/app/hourly_brief/worker.py：小时任务和 5 秒决策任务。
