# SQLite 采集表架构说明

本项目的在线采集采用三张表：`telemetry_sources` 保存来源运行状态，`telemetry_points` 保存点位定义和最新样本，`telemetry_readings` 保存历史样本。它们解决三个不同的问题：采集器是否在线、某个仪表现在读到什么、过去读到过什么。

当前数据库为 `backend/data/dense_medium.db`。2026-10-06 核对时已有 1 个采集来源、54 个点位，历史行数随采集持续增长。以下说明对应已运行的实现。

日常查看直接使用 `online_instruments` 简表视图，只显示设备、标签名、说明、ItemID、值、时间六列。它读取每个启用点位的最新快照，时间为该点的本机接收时间；可能包含离线前或质量异常时的最后读数。网页通过灰色值和提示保留不可用原因。本地浏览窗口默认每 5 秒刷新这张简表，原始表与 SQL 放在“高级查询”中。

[打开 Archify 表关系图](archify/architecture-telemetry-tables-20261006-103547/telemetry-tables.html)。图中虚线表示由应用维护的逻辑关联，实际 SQLite 尚未声明数据库外键。

## 三张表的关系

```text
一个采集来源
  telemetry_sources.source_id
       │ 1 对多：source_id
       ▼
多个仪表点位
  telemetry_points.(source_id, key)
       │ 1 对多：source_id + key
       ▼
每个点位的多条历史
  telemetry_readings.(source_id, point_key)
```

例如，同一个 `kepserver-main` 来源下面有 403 密度、404 密度、液位、煤量等点位。403 密度在点位表中只有一行，这行的 `latest` 持续更新；它在历史表中可以有很多行，每行代表一次被保留的样本。

新增仪表通过增加点位行完成，采集表结构保持统一。查询当前值直接读点位表，查询趋势再读历史表，因此当前值查询不会随着历史积累而扫描大量历史记录。

## 采集来源表

`telemetry_sources` 记录采集器的运行状态。每个来源一行，主键是 `source_id`；主键用于唯一识别一行。

| 字段 | 声明类型 | 用途 |
|---|---|---|
| `source_id` | VARCHAR(64)，主键 | 稳定来源标识，如 `kepserver-main` |
| `name` | VARCHAR(128) | 来源显示名称 |
| `state` | VARCHAR(24) | connecting、connected、retrying、stopped、fault 等状态 |
| `owner` | VARCHAR(36)，可空 | 当前采集实例的 UUID 标识，实际生成 32 位字符串；不是 Windows PID |
| `lease_until` | VARCHAR(32)，可空 | 当前实例持有该来源写入权的截止时间 |
| `heartbeat_at` | VARCHAR(32)，可空 | 最近一次运行状态或持久化续租时间 |
| `last_sample_at` | VARCHAR(32)，可空 | 已入库样本的最近接收时间 |
| `error_code` | VARCHAR(64)，可空 | 最近的采集错误类型 |
| `retry_seconds` | FLOAT | 当前重连等待时间 |

`owner` 和 `lease_until` 组成租约：一个采集实例在限定时间内持有该来源。默认配置对应约 60 秒租期；活跃实例会续租，第二个实例不能在租约未到期时接管。另一实例接管后，旧实例的 owner 不再匹配，后续写入被拒绝。

这张表的 `connected` 不能单独证明来源仍在线。查询接口还检查租约是否有效；进程意外退出后，数据库可能仍保留 connected，接口会在租约过期后显示 offline。

服务器端点、轮询间隔、安全策略和证书路径由 `backend/config/kepserver.local.json` 管理，当前没有保存在这张状态表中。

## 点位与最新样本表

`telemetry_points` 同时保存仪表定义和最新样本。复合主键 `(source_id, key)` 表示两个字段共同识别一行：不同来源可以使用相同 key，但同一来源内不能重复。

| 字段 | 声明类型 | 用途 |
|---|---|---|
| `source_id` | VARCHAR(64)，复合主键第 1 项 | 所属采集来源 |
| `key` | VARCHAR(64)，复合主键第 2 项 | 本项目的点位标识 |
| `config` | JSON | 完整点位定义 |
| `enabled` | BOOLEAN | 是否属于当前启用的点表 |
| `latest` | JSON，可空 | 最近收到的样本；尚未采到时为空 |
| `last_history_at` | VARCHAR(32)，可空 | 最近一次历史样本的接收时间，用于控制历史保存频率 |

`config` 包含 `key`、`name`、`node_id`、`unit`、`value_type`、`scale`、`offset`、`minimum`、`maximum`、`max_age_seconds` 和 `max_source_age_seconds`，另有展示元数据 `device`、`tag_name`、`description`、`item_id`。现场元数据按 Excel 原字段精确填充，变更这些展示字段不清空已有读数，也不改变采样定义指纹。

其中 NodeId 是远程 KEPServer 的寻址标识，key 是本项目点位身份。本次点表采用 `tag_` 加 Item ID 的 SHA-256 前 20 位生成 key；同一 Item ID 重新生成时保持一致。标签改名会改变 Item ID，需要评估新旧点位的关联，不能把它当作永久不变的设备资产编号。

`latest` 是最近收到的样本，包含 Bad 或 Uncertain 样本，不是“最后一次 Good”。保存坏质量样本能让界面如实显示当前异常。点位从配置中移除时，旧行被禁用，已有最新值和历史保留；查询当前点表时只展示 enabled 点。

## 历史读数表

`telemetry_readings` 每行保存一个点位的一次历史样本。多个点位同一轮读取共享一个 batch_id，但各自占一行。

| 字段 | 声明类型 | 用途 |
|---|---|---|
| `id` | INTEGER，主键 | 数据库生成的行标识，用于历史分页 |
| `source_id` | VARCHAR(64) | 样本所属来源 |
| `point_key` | VARCHAR(64) | 对应点位表的 key |
| `batch_id` | VARCHAR(36) | 采集批次的 UUID 标识 |
| `received_at` | VARCHAR(32) | 本机接收时间，方便索引和历史清理 |
| `sample` | JSON | 该次采集的完整样本 |

实际 DDL 使用 INTEGER PRIMARY KEY，没有显式的 SQLite AUTOINCREMENT 关键字，因此 id 不应被当作永不复用的业务编号。历史接口按 id 倒序分页，这代表入库顺序；缓存重放时，入库顺序可能与测量时间顺序不同。

唯一约束 `(source_id, point_key, batch_id)` 防止同一来源、同一点、同一批次重复插入历史。重复处理同一已保存批次不会新增重复行，这就是该处的幂等保证。历史采用限频保存，未入历史的批次没有独立永久账本。

两个普通索引各有用途：

| 索引 | 字段 | 用途 |
|---|---|---|
| `ix_telemetry_point_time` | source_id、point_key、received_at | 按来源、点位和接收时间定位历史 |
| `ix_telemetry_retention` | received_at | 查找过期历史 |

当前历史接口使用 id 倒序；SQLite 实测会先用点位时间索引筛选，再使用临时排序。历史量增长后，可评估增加 `(source_id, point_key, id)` 索引，适配接口分页方式。

## 样本 JSON 与数据可用性

点位表的 `latest` 和历史表的 `sample` 使用相同结构：

| JSON 字段 | 含义 |
|---|---|
| `key`、`name`、`node_id`、`unit` | 该次采集的点位身份、名称、地址和单位 |
| `raw_value` | 读取的原始标量值 |
| `value` | 按 `raw_value × scale + offset` 计算的值；类型不匹配等情况可为空 |
| `status_code` | OPC UA 原始质量状态码 |
| `quality` | good、uncertain 或 bad |
| `issue` | 类型不匹配、量程外、非有限值、源时钟异常等原因；正常时为空 |
| `source_at` | 源侧时间戳，可能是最近值变更时间 |
| `server_at` | KEPServer 返回的服务器时间戳 |
| `received_at` | 本项目接收到这一批数据的时间 |
| `definition_id` | NodeId、单位、缩放、偏移、类型和量程的 SHA-256 指纹 |

时间使用带时区的 UTC ISO 字符串保存，界面再转换为本机时区。数据库声明 JSON 类型，当前写入内容实际是序列化文本；可用 SQLite 的 `json_extract` 读取其中的字段。

`available` 和接口 `status` 没有作为列保存。它们在查询时根据样本 issue、来源状态与租约、接收时间新鲜度，以及可选的源时间限制计算。这样，采集器停止后，旧读数仍能供核对，但会显示不可用。0 和 false 都是合法值，不能按真假判断数据缺失；null 才表示没有数值。

Good 只表示 OPC UA 质量状态。本次仍有单位、量程待确认，累计煤量点也出现过异常量级；协议可读取不等于已经确认仪表标定和业务含义。

## 一批数据如何写入

1. 采集实例取得来源租约，按配置连接 KEPServer，只读获取点位值及时间戳。
2. 数据规则检查类型、质量、有限值、已配置量程和源时钟，并保留原值与问题原因。
3. 整批样本先写入磁盘批次文件，完成落盘后再尝试写数据库。
4. 数据库在一个事务中处理整批数据：更新点位最新样本，按条件追加历史，并更新来源心跳和最近采样时间。事务提交失败时，这一批数据库改动整体回滚。
5. 提交成功后删除对应批次文件。重启后先重放剩余文件，再继续新采样。

SQLite 写入使用 `BEGIN IMMEDIATE`；数据库启用 WAL，采集和网页读取使用短连接、短事务。完整读取并成功落盘的批次可以重放，但网络断线期间没有读到的 PLC 值不能凭客户端补出。

最新样本只有在定义指纹一致、接收时间不早于已有样本时才更新，避免旧缓存回退当前值。NodeId、单位、缩放、类型等定义变化时，旧 latest 被清空；旧批次可能按历史规则保存，但不能冒充新定义的最新值。`definition_id` 是指纹，不是完整配置版本；当前没有保存每次配置变更的版本表。

## 更新频率与保留规则

当前配置约每 5 秒读取一批并更新最新值。每点历史达到 60 秒间隔时保存一次，质量或 issue 变化时额外保存；单纯数值变化不会使每轮都入历史。因此历史是限频抽样，不是所有采样的完整流水，也没有分钟均值、最大值或最小值的聚合。

历史默认保留 7 天。成功采集循环约每分钟检查一次清理条件，每轮最多删除该来源 5000 条过期历史；持续故障或大量积压时不会保证过期行立即删除。清理历史不会删除点位配置和 latest。

## 为什么当前使用 JSON

关系字段、批次、接收时间独立成列，便于关联、去重和索引；样本细节使用 JSON，便于同时保存数值、布尔值、质量和不同时间信息。对当前 54 点的接入阶段，这能保持实现简单，增加样本描述字段时也不必频繁修改表结构。

代价是单位、NodeId、样本值等没有独立数据库列约束，查询需要 `json_extract`，目前也没有为这些 JSON 内部字段建立专门索引。大量报表、聚合或更高频数据到来时，应评估把常查字段独立成列，以及将点位定义和最新值拆成不同表。

当前关联完整性由代码维护；将来建立数据库外键前，要核查已有数据、禁用点位和历史保留规则。当前没有配置版本历史、单独的采集批次审计表或分钟统计表，这些应随追溯和分析需求补充。上述取舍解释当前实现，不是已经完成全部工业数据管理能力。

## 在只读浏览窗口中查询

日常只需查询六列简表：

```sql
SELECT * FROM online_instruments
ORDER BY "设备", "标签名";
```

查看采集来源状态：

```sql
SELECT source_id, name, state, heartbeat_at, last_sample_at
FROM telemetry_sources;
```

查看 54 个点的最新值和原值：

```sql
SELECT
  key,
  json_extract(config, '$.name') AS point_name,
  json_extract(config, '$.node_id') AS node_id,
  json_extract(latest, '$.raw_value') AS raw_value,
  json_extract(latest, '$.value') AS value,
  json_extract(latest, '$.quality') AS quality,
  json_extract(latest, '$.received_at') AS received_at
FROM telemetry_points
WHERE source_id = 'kepserver-main' AND enabled = 1;
```

查看 403 密度点最近保存的历史：

```sql
SELECT id, received_at,
       json_extract(sample, '$.raw_value') AS raw_value,
       json_extract(sample, '$.value') AS value,
       json_extract(sample, '$.quality') AS quality
FROM telemetry_readings
WHERE source_id = 'kepserver-main'
  AND point_key = (
    SELECT key FROM telemetry_points
    WHERE source_id = 'kepserver-main'
      AND json_extract(config, '$.node_id') =
          'ns=2;s=TIA_3_2.TIA_3_2.403/MD'
  )
ORDER BY id DESC
LIMIT 100;
```

SQLite `json_extract` 对 JSON 布尔值返回 0 或 1，原始 JSON 中仍保留 false 或 true。上面的 value、quality、node_id 等是查询生成的列名，不是原表的独立列。

## 与原业务表的边界

采集三表保存仪表观测；原有 `coal_records`、`heavy_samples`、`manual_entries`、模型和设置表承担化验、人工输入和计算业务。浏览器的 `/state` 整库镜像不覆盖采集三表，采集器也不改写这些业务表。

当前在线点位尚未映射到密度建议计算输入。后续需要明确哪个物理点对应哪个生产系统、指标、单位及优先级，再由业务取值层使用采集值；这一步应独立于采集存储，保持 GPT 与 DS 的模型边界。
