# 分层存储与安全清理

2026-10-23 用户批准，并进一步将入库频率改为1分钟。此策略替代此前原始明细永久保存的约定；实时采集仍为5秒，常规历史采集及逐次决策改为60秒。DS模型、训练、对拍数据及预测分支不变。

## 保留范围

| 数据 | 策略 |
|---|---|
| 原始采集、原始逐次决策 | 在线30天，按完整小时逐步迁移 |
| 冷明细 | 按月份目录、小时分片，保留到原时段结束后365天 |
| 小时统计、小时建议及依据 | 永久保留 |
| 小时化学计算所需的最小原始预测、权重及停机依据 | 永久保留；支持晚补重介化验与分钟统计 |
| 人工化验、补录、调密操作、反馈、模型和配置版本 | 永久保留 |
| 全量备份 | 同一安装的最新2个完整验证恢复点，加1个明确稳定回滚点 |
| 已关闭普通日志／错误日志 | 30／90天；混合网页日志按错误日志保留90天 |

30天按UTC连续24小时计算，小时结束时间必须早于保留边界。维护逐步追赶，存在积压时可能多留，不能把“已启用”解释为当日即只剩30天。始终保留最高原始记录ID的一行，避免SQLite整数主键在全表清空后复用。被仍在线决策引用的原始记录也会多留，绝不以首次引用时间判断过期。归档进度边界前90秒的原始记录也暂时保留，直到下一小时的永久计算依据冻结，防止未被直接引用的坏质量事件提前丢失。

## 运行方式

- 仅生产网页进程启用独立维护任务。只读笔记本不启动清理，也不能通过维护CLI写生产数据。
- 启动后先等待60秒；每次最多处理一个小时归档和500条原始删除。SQLite维护连接等锁上限250毫秒，忙时退避。
- 全历史引用分小时回填最大使用slot，读取解析在写锁之外。历史扫描完成后才能释放原始引用保护。
- 月目录下使用小时分片，避免等待整月到期造成在线多留一个月。最多4个正在删除的小时，限制待清理清单占用。
- 归档、恢复验证临时文件和网页关闭日志分卷均由实际数据目录派生；迁移到D盘后也在D盘。程序代码和当前诊断日志位置保留。
- 不在小时统计请求中归档；不执行全库检查、自动VACUUM或PLC写操作。

## 删除前的证明

1. 读取原始逐次输出、原始采集及其引用、90秒边界证据、手工依据、模型上下文和原冻结小时。
2. 永久保存最小化学帧、原质量截断权重与停机区间。不会调用当前模型伪造旧预测。
3. 将原始引用形式和已解引用的决策同时写入压缩归档。表数据带类型、行数及校验和；目录带版本化清单与SHA-256。
4. 在同一数据盘的新SQLite文件中完整试恢复并回读比对，再原子发布归档。
5. 短事务重查原小时与热明细身份、正文、采集集合；变化即保留原数据并重试。
6. 后续每批删除前复核归档压缩文件校验和、原始行收据及最大引用slot。引用未释放、源行改变或校验失败时保留记录。

损坏归档不回退成当前读数。一年以上逐次详情返回明确的过期状态；小时统计和人工记录继续保留。原化学帧保留真实5／30／60秒粒度，不因新配置重算旧覆盖率。

60秒主批之外，质量变化仍单独保存。为保持模型液位提前90秒的物理口径，每分钟最多另存一条必要的原始液位对齐证据，保留原采样时间、原批次及质量，不能用当前液位替代、放宽滞后容差或将辅助证据当成60秒有效覆盖。实时5秒数据仅保留有界短缓存，不把全部5秒数据写入历史库。

## 状态和人工维护

浏览器查看 `/api/v1/storage-retention/status`，包含策略、引用回填进度、归档与清理状态。旧主机未安装此功能时，测试端可继续读取原有数据。

在项目根目录执行：

```powershell
.\backend\.venv\Scripts\python.exe .\backend\scripts\storage_retention.py status
.\backend\.venv\Scripts\python.exe .\backend\scripts\storage_retention.py preview-files
```

离线安装若使用 `runtime\python.exe`，替换上述解释器路径即可。`preview-files`只预览认证备份／关闭日志，不登记未知文件。

需要临时推进一次受同样保护的维护单元时使用 `tick`。通常无需手动运行，后台会自动推进；操作系统锁防止同一安装多任务重叠。

冷归档恢复到**新隔离文件**，不能覆盖生产数据库：

```powershell
.\runtime\python.exe .\backend\scripts\storage_retention.py restore --archive "D:\DshDensityControlData\data\retention\archives\2026-10\小时分片\manifest.json" --destination "D:\ArchiveReview\restored.sqlite"
```

恢复文件可独立查询，不是直接替换生产库的数据库备份。原列定义仅作元数据，恢复不会执行清单中的SQL、索引或触发器。

## 备份保护

- 更新前的一致快照不等于完整内容验证成功。结构检查通过、`deferred`或检查超时的备份均不能当作已验证恢复点。
- 复用现有更新流程的完整检查结果，不为认证再次扫描7GB数据库。普通恢复备份只有小库才尝试短预算检查。
- 本次发布显式使用 `--defer-large-snapshot-check`：超过64MiB的更新前备份仍一致复制并验证结构，但将内容全检留到维护窗口，记录 `deferred_manual / passed=False`。该备份受未验证保护；不会因此清理旧稳定点。小库及未选择该参数的旧更新流程不变。
- 两类备份目录共同使用实际数据及备份目录的安全共同根登记。特殊跨盘或盘根布局无法安全合并时，保守保护并报告。
- 稳定点须明确验证/指定；没有可确认的稳定恢复点时不删除全量备份。未知旧备份、旧独立清单、正在写入、被修改或路径异常的文件始终保护。
- 因此最初的旧备份可能多留。不能为了达到“三份”数量而把未验证文件自动认定可靠，也不自动清空迁移前备份。

需要显式选定**已认证**稳定点时，先根据预览确认ID，再运行：

```powershell
.\runtime\python.exe .\backend\scripts\storage_retention.py stable-backup --backup-root "D:\DshDensityControlData" --backup-id "已验证备份ID"
```

## 物理空间

SQLite删除后的页由后续写入复用，主库文件不会立刻缩小。日常限期清理用于控制持续增长；现有大文件的物理压缩应单独安排维护窗口、备份与可用空间，不能和在线采集一起执行大规模VACUUM。

主机更新包需显式使用 `--history-interval-seconds 60 --defer-large-snapshot-check` 构建；不带入库参数的更新不会擅自改动已安装配置，旧30秒包仍可兼容。

首次运行及主机更新验收必须核对：采集继续推进、60秒主历史继续推进、即时与小时接口可用、90秒液位依据正确、只读测试服仍连接主机、原小时及DS基线不变。不要用“进程已启动”代替连接与数据推进验证。
